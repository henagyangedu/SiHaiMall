# 开放接口

给 ERP、财务、物流等外部系统对接四海商城用的接口：读取订单、回传发货、同步库存、拉取支付流水和售后单。

> 两种用法可以一起用：对方定时来拉数据（第三到六节），或者让商城在订单付款、发货、退款时主动通知对方（第七节“主动推送”）。接口在 1.0 之前可能调整，升级前请看[更新日志](../CHANGELOG.md)。

## 一、开始之前

**拿密钥**

商城管理员在后台“设置 → 开放接口”里新建一个应用，勾选需要的权限，得到一把密钥（以 `shm_` 开头）。密钥只在生成时显示一次，丢了只能重新生成，重新生成后旧的马上失效。

**接口地址**

```
https://商城后端的域名/open-api/v1
```

下文的地址都接在它后面。必须用 HTTPS。

**身份校验**

每个请求都在请求头里带上密钥：

```
Authorization: Bearer shm_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

**先调一下连通测试**

```bash
curl -H "Authorization: Bearer 你的密钥" https://商城后端的域名/open-api/v1/ping
```

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "app": "金蝶 ERP",
    "scopes": ["order.read", "order.ship"],
    "timezone": "Asia/Shanghai",
    "time": "2026-10-12 10:30:00"
  }
}
```

## 二、通用约定

**返回格式**

所有接口都返回 JSON：`code` 为 0 表示成功，`data` 是结果；不为 0 表示失败，`msg` 是中文的原因。**HTTP 状态码通常是 200，成功与否请看 `code`。**

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 1 | 业务上不允许（如订单不是待发货），原因见 `msg` |
| 401 | 没带密钥、密钥无效、应用已停用，或来源 IP 不在白名单里 |
| 403 | 这把密钥没有这个接口需要的权限 |
| 404 | 订单、售后单不存在，或接口地址写错了 |
| 422 | 参数不对，`msg` 是第一条问题，`data` 里按字段列出全部问题 |
| 429 | 调得太频繁。每个接口每个来源 IP 每分钟最多 300 次，过一分钟再试 |
| 500 | 商城内部出错，可以稍后重试 |

**权限**

| 权限 | 能做什么 |
| --- | --- |
| `order.read` | 读取订单（含收货信息）、快递公司编码 |
| `order.ship` | 发货、修改物流单号 |
| `goods.read` | 读取规格和库存 |
| `stock.write` | 修改库存 |
| `finance.read` | 读取支付流水和售后单 |

**时间**

所有时间都是商城的时区（`ping` 返回的 `timezone`，默认北京时间），格式 `年-月-日 时:分:秒`，如 `2026-10-12 10:30:00`。传进来的时间参数也按这个时区理解。

**金额**

金额都是字符串（如 `"128.00"`），请不要转成浮点数计算。订单的金额是下单币种的，币种在 `currency` 里。

**分页**

列表接口都支持 `page`（从 1 开始）和 `page_size`（默认 50，最大 100），返回 `total`、`page`、`page_size`。

**增量拉取**

订单、支付流水、售后单的列表都按更新时间从早到晚排，支持 `updated_after`（大于等于）和 `updated_before`（小于）。推荐的做法：

1. 记下上一次拉到的最后一条的 `updated_at`。
2. 下一次把它作为 `updated_after`，一页一页拉到最后。
3. 边界上的那几条会重复出现，请按单号去重（按单号“有则更新、无则新增”即可）。

## 三、订单

### 订单列表

`GET /orders`　权限 `order.read`

| 参数 | 说明 |
| --- | --- |
| `updated_after` / `updated_before` | 更新时间范围 |
| `status` | 订单状态，见下表 |
| `pay_status` | 支付状态，见下表 |
| `page` / `page_size` | 分页 |

订单的状态变化、发货、改物流单号都会刷新 `updated_at`。

```bash
curl -G -H "Authorization: Bearer 你的密钥" \
  --data-urlencode "status=1" \
  --data-urlencode "updated_after=2026-10-12 00:00:00" \
  https://商城后端的域名/open-api/v1/orders
```


字段说明：

- **金额的关系**：`goods_amount`（商品）+ `shipping_fee`（运费）− `bundle_amount`（套餐优惠）− `discount_amount`（会员折扣）− `coupon_amount`（优惠券）− `points_amount`（积分抵扣）+ 价外税 = `pay_amount`（实付）。
- **税**：`tax_included` 为 `false` 时 `tax_amount` 是另加的税，已经算在 `pay_amount` 里；为 `true` 时是含在价格里的税，`pay_amount` 不因它变化。
- `base_pay_amount`：实付金额折成商城基准币种后的数。`rate` 是下单时的汇率。
- `refunded_amount`：已经退完成的金额合计。
- `items[].id`：商品行的编号，分批发货时用它指定发哪几行。
- `items[].sku_sn`：规格的货号。取的是规格**现在**的货号（订单里没有保存下单时的货号），规格已删除时是空串。
- `items[].price`：下单币种的成交单价。`items[].refund_qty`：已经退掉的件数。
- `address`：无需发货的虚拟商品订单没有收货信息，这一项是 `null`。国内地址的省、市是标准名称；境外地址的省 / 州、城市是买家手填的文字。
- `shipments`：发货记录，见“发货”。

**订单状态 `status`**

| 值 | 含义 |
| --- | --- |
| 0 | 待支付 |
| 1 | 待发货 |
| 2 | 待收货（已全部发出） |
| 3 | 已完成 |
| 4 | 已取消 |
| 5 | 售后中（有没处理完的售后，这期间不能发货） |
| 6 | 已关闭（超时未付款，或商品全部退款） |

**支付状态 `pay_status`**

| 值 | 含义 |
| --- | --- |
| 0 | 未支付 |
| 1 | 已支付 |
| 2 | 部分退款 |
| 3 | 已退款 |

要发货的订单是 `status=1` 的。

### 订单详情

`GET /orders/{订单号}`　权限 `order.read`

返回的 `data` 就是列表里的一条。

### 快递公司编码

`GET /express-companies`　权限 `order.read`

返回发货时可以用的 `express_code`：

```json
{ "code": 0, "msg": "ok", "data": [ { "code": "SF", "name": "顺丰速运" }, { "code": "ZTO", "name": "中通快递" }, { "code": "OTHER", "name": "其它" } ] }
```

## 四、发货

### 发货

`POST /orders/{订单号}/ship`　权限 `order.ship`　请求体是 JSON

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `express_code` | 是 | 快递公司编码。不在列表里的传 `OTHER` |
| `express_name` | `OTHER` 时必填 | 快递公司名称 |
| `express_no` | 是 | 快递单号 |
| `item_ids` | 否 | 只发其中几个商品行（`items[].id` 的数组）。不传 = 把还没发的全部发出 |

```bash
curl -X POST -H "Authorization: Bearer 你的密钥" -H "Content-Type: application/json" \
  -d '{"express_code":"SF","express_no":"SF1234567890"}' \
  https://商城后端的域名/open-api/v1/orders/2026101210300012345/ship
```

```json
{
  "code": 0,
  "msg": "ok",
  "data": { "id": 88, "express_code": "SF", "express_name": "顺丰速运", "express_no": "SF1234567890", "item_ids": [501], "shipped_at": "2026-10-12 15:02:11" }
}
```

要点：

- 只有已付款、状态是“待发货”的订单能发。售后中的订单要等售后处理完。
- **分批发货**：用 `item_ids` 一次发一部分。全部商品行都发出后，订单才变成“待收货”；在这之前状态仍是“待发货”，哪些行发了看 `items[].shipped`。已经全部退款的商品行不用发。
- **可以放心重试**：同一张订单用同一个快递公司和单号再提交一次，会直接返回上一次的发货记录，不会发两次，也不会报错。请求超时后原样重发即可。
- 发货后商城会通知买家（站内信；商家开了邮件通知的话还有邮件）。
- 国内快递由商城的物流查询服务商查轨迹，所以国内快递请尽量用列表里的编码，不要都传 `OTHER`。

### 修改物流单号

`PUT /shipments/{发货记录的 id}`　权限 `order.ship`　请求体是 JSON

参数是 `express_code`、`express_name`、`express_no`，含义同上。单号填错时用它更正；返回更正后的发货记录。只有待发货、待收货、已完成的订单能改（售后中、已取消、已关闭的不能）。

## 五、规格和库存

商城里一个商品有一个或多个规格（SKU），库存和价格都在规格上。

### 规格列表

`GET /skus`　权限 `goods.read`

| 参数 | 说明 |
| --- | --- |
| `sku_sn` | 按货号查，多个用英文逗号分开 |
| `goods_id` | 只看某个商品的规格 |
| `page` / `page_size` | 分页 |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "list": [
      {
        "sku_id": 34,
        "goods_id": 12,
        "sku_sn": "DEMO-FEEDER-01",
        "title": "智能喂食器",
        "spec_text": "白色 / 4L",
        "price": "128.00",
        "market_price": "168.00",
        "stock": 57,
        "weight": "1.200",
        "volume": "0.000",
        "enabled": true,
        "on_sale": true,
        "updated_at": "2026-10-10 09:00:00"
      }
    ],
    "total": 1,
    "page": 1,
    "page_size": 50,
    "currency": "CNY"
  }
}
```

- `price` 是基准币种（`currency`）的标准价，不含按币种、按销售区域单独定的价。
- `title`、`spec_text` 是商城默认语言的。
- `enabled`：这个规格是否启用；`on_sale`：所属商品是否上架。两个都是 `true` 买家才买得到。
- `updated_at` 是规格资料最后一次修改的时间。**买家下单扣库存不会刷新它**，所以不能用它做库存的增量同步；要对库存请按货号或分页整体拉取。
- 已删除的商品不在列表里。

### 修改库存

`POST /stock`　权限 `stock.write`　请求体是 JSON

```json
{
  "items": [
    { "sku_sn": "DEMO-FEEDER-01", "qty": 80 },
    { "sku_id": 35, "mode": "add", "qty": -3, "remark": "盘点" }
  ]
}
```

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `items` | 是 | 一次最多 100 条 |
| `items[].sku_id` / `items[].sku_sn` | 二选一 | 用规格 ID 或货号指定规格。两个都传时用 `sku_id` |
| `items[].mode` | 否 | `set`（默认）：把库存改成 `qty`；`add`：在现在的基础上加 `qty`，负数是减 |
| `items[].qty` | 是 | 整数 |
| `items[].remark` | 否 | 写进商城库存日志的说明，最多 100 字 |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "results": [
      { "sku_id": 34, "sku_sn": "DEMO-FEEDER-01", "ok": true, "stock": 80, "msg": "" },
      { "sku_id": 35, "sku_sn": "DEMO-FEEDER-02", "ok": false, "stock": null, "msg": "库存不能小于 0，当前库存 2" }
    ]
  }
}
```

要点：

- **一条一条处理，互不影响。** 外层 `code` 为 0 只表示请求被接受，**每一条成没成功要看 `results` 里对应那条的 `ok`**；`results` 的顺序和提交的顺序一致。
- **货号要唯一才能用货号改库存。** 商城后台不强制货号唯一，同一个货号对应多个规格时这一条会被拒绝，请让商家把货号改成唯一的，或改用 `sku_id`。
- **`set` 和 `add` 怎么选**：外部系统是库存的唯一来源时用 `set`，但要注意它会盖掉两次同步之间买家下单扣掉的数量——同步前请先把商城里已付款未发货的订单量算进去，或者同步得足够勤。只是登记出入库的变化量时用 `add`，它不会盖掉买家下单的扣减。
- 库存不能改成负数。数量没有变化时不写库存日志。
- 买家下单时商城自己会扣库存，取消订单、退款会回补，这些不需要外部系统处理。

## 六、财务

### 支付流水

`GET /pay-trades`　权限 `finance.read`

| 参数 | 说明 |
| --- | --- |
| `updated_after` / `updated_before` | 更新时间范围 |
| `trade_type` | 1 收款，2 退款 |
| `status` | 0 待支付，1 成功，2 失败，3 已关闭 |
| `page` / `page_size` | 分页 |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "list": [
      {
        "trade_no": "P2026101210300098765",
        "order_no": "2026101210300012345",
        "trade_type": 1,
        "channel": "alipay",
        "channel_trade_no": "2026101222001400000000000001",
        "currency": "CNY",
        "amount": "261.00",
        "fee_amount": "0.00",
        "status": 1,
        "status_text": "成功",
        "paid_at": "2026-10-12 10:30:00",
        "created_at": "2026-10-12 10:29:10",
        "updated_at": "2026-10-12 10:30:00"
      }
    ],
    "total": 1,
    "page": 1,
    "page_size": 50
  }
}
```

- 一笔收款、一笔退款各是一条。对账一般只看 `status=1` 的。
- `channel`：支付渠道（`stripe`、`paypal`、`wechat`、`alipay` 等）。`channel_trade_no`：渠道那边的交易号，还没拿到时是空串。
- 买家发起了支付但没付成的，也会有一条 `status` 不是 1 的记录。
- **线下收款的订单没有支付流水**（后台直接标记为已付款的），这类订单请以订单列表里的 `pay_amount` 和 `paid_at` 为准。
- `fee_amount`：渠道手续费。只有渠道在回调里给了手续费时才有数，否则是 0，**不能把 0 当成“没有手续费”**，手续费请以渠道账单为准。

### 售后单列表

`GET /refunds`　权限 `finance.read`

| 参数 | 说明 |
| --- | --- |
| `updated_after` / `updated_before` | 更新时间范围 |
| `status` | 售后单状态，见下表 |
| `order_no` | 只看某张订单的 |
| `page` / `page_size` | 分页 |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "list": [
      {
        "refund_no": "R2026101311000054321",
        "order_no": "2026101210300012345",
        "order_item_id": 501,
        "type": 2,
        "type_text": "退货退款",
        "status": 4,
        "status_text": "已完成",
        "qty": 1,
        "currency": "CNY",
        "refund_amount": "125.55",
        "reason": "尺寸不合适",
        "reject_reason": "",
        "return_express": "中通快递",
        "return_express_no": "ZT0000000001",
        "refund_trade_no": "2026101322001400000000000002",
        "created_at": "2026-10-13 11:00:00",
        "finished_at": "2026-10-14 16:20:00",
        "updated_at": "2026-10-14 16:20:00"
      }
    ],
    "total": 1,
    "page": 1,
    "page_size": 50
  }
}
```

- `order_item_id`：退的是订单里的哪个商品行；**0 表示整单退款**（含运费，只发生在还没发货的订单上）。
- `refund_amount`：退款金额。“已完成”的才是真的退出去了的钱。
- `refund_trade_no`：渠道的退款单号；线下退款时为空。

**售后单状态 `status`**

| 值 | 含义 |
| --- | --- |
| 0 | 待审核 |
| 1 | 待买家退货 |
| 2 | 待确认收货（买家已寄回） |
| 3 | 退款中 |
| 4 | 已完成 |
| 5 | 已拒绝 |
| 6 | 已撤销 |

### 售后单详情

`GET /refunds/{售后单号}`　权限 `finance.read`

返回的 `data` 就是列表里的一条。

## 七、主动推送（Webhook）

订单付款、发货、退款这些事情发生时，商城主动向你提供的地址发一条通知，你不用每隔几分钟来查一次。

### 开通

请商城管理员在后台“设置 → 开放接口”里编辑你的应用，填上**接收地址**、勾选要**通知哪些事**、打开推送。第一次填接收地址时会生成一把**签名密钥**（`whsec_` 开头，和调用接口用的密钥不是同一把），只显示一次，请管理员交给你。

接收地址的要求：`https://` 开头，公网能访问（不能是内网或本机地址），不会跟随跳转。

### 事件

| 事件 | 什么时候发 | 应用要有的权限 |
| --- | --- | --- |
| `order.paid` | 订单付款成功 | `order.read` |
| `order.shipped` | 每发出一个包裹（分批发货时每批一条） | `order.read` |
| `order.completed` | 订单完成（买家确认收货、自动收货、虚拟商品付款即完成） | `order.read` |
| `order.closed` | 订单取消或关闭（买家或商家取消、超时未付款、商品全部退完） | `order.read` |
| `refund.created` | 买家申请售后，或商家代买家发起 | `finance.read` |
| `refund.completed` | 退款完成 | `finance.read` |
| `ping` | 管理员在后台点了“发送测试通知” | 无 |

下单但还没付款不通知。修改物流单号、售后被拒绝或撤销、库存变动、支付流水目前没有通知，要用拉取接口。

### 通知的样子

商城向接收地址发一个 `POST`，正文是 JSON：

```json
{
  "id": "6f1c2a9e4b7d4c0f9a3e5d2b8c1f7a60",
  "event": "order.shipped",
  "created_at": "2026-11-02 14:03:27",
  "data": {
    "order_no": "202611021403270001",
    "status": 2,
    "pay_status": 1,
    "pay_amount": "258.00",
    "currency": "CNY",
    "shipment_id": 31,
    "express_code": "SF",
    "express_name": "顺丰速运",
    "express_no": "SF1234567890"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `id` | 这条通知的唯一编号（32 位）。重试、重发时不变，**用它去重** |
| `event` | 事件 |
| `created_at` | 事情发生的时间（北京时间） |
| `data` | 见下 |

`data` 的内容：

- 订单事件：`order_no`、`status`、`pay_status`、`pay_amount`、`currency`（状态码的含义见“订单列表”）。`order.shipped` 另有 `shipment_id`、`express_code`、`express_name`、`express_no`。
- 售后事件：`refund_no`、`order_no`、`type`、`status`、`refund_amount`、`currency`（含义见“售后单列表”）。
- `ping`：只有一句 `message`。

**通知是“薄”的**：只告诉你哪张单发生了什么，不带收货人、商品明细这些内容。需要详情请用 `GET /orders/{订单号}` 或 `GET /refunds/{售后单号}` 再取一次——这样拿到的一定是最新的数据。`data` 里的状态是发出通知那一刻的，仅供参考。

请求头：

| 请求头 | 说明 |
| --- | --- |
| `X-Shm-Event` | 事件，和正文里的 `event` 相同 |
| `X-Shm-Delivery` | 通知编号，和正文里的 `id` 相同 |
| `X-Shm-Timestamp` | 发送时间，Unix 时间戳（秒）。每次重试都是新的 |
| `X-Shm-Signature` | 签名，`sha256=` 加 64 位十六进制 |
| `Content-Type` | `application/json` |
| `User-Agent` | `SihaiMall-Webhook/1` |

### 验证签名

**一定要验证**，否则任何知道你地址的人都能伪造通知。

签名 = `HMAC-SHA256(签名密钥, 时间戳 + "." + 收到的正文原文)`，十六进制小写。注意用**收到的原始正文**来算，不要先解析成对象再转回字符串。

PHP：

```php
$body = file_get_contents('php://input');
$ts   = $_SERVER['HTTP_X_SHM_TIMESTAMP'] ?? '';
$want = 'sha256=' . hash_hmac('sha256', $ts . '.' . $body, $secret);
if (!hash_equals($want, $_SERVER['HTTP_X_SHM_SIGNATURE'] ?? '') || abs(time() - (int) $ts) > 300) {
    http_response_code(401);
    exit;
}
```

Node.js：

```js
const crypto = require('crypto')
// rawBody 是收到的原始正文（字符串或 Buffer），不是解析后的对象
const want = 'sha256=' + crypto.createHmac('sha256', secret).update(ts + '.' + rawBody).digest('hex')
const got = req.headers['x-shm-signature'] || ''
const ok = got.length === want.length && crypto.timingSafeEqual(Buffer.from(got), Buffer.from(want))
```

建议同时检查时间戳和现在相差不超过 5 分钟，防止有人把截获的旧通知重新发给你。

### 怎么算收到，没收到会怎样

- **5 秒内返回 HTTP 2xx** 就算收到，返回的内容不看。请先应答、再慢慢处理，不要在应答之前做耗时的事。
- 超时、连不上、返回其他状态码都算没收到，之后会重试：隔 1 分钟、5 分钟、30 分钟、2 小时、6 小时、24 小时，**最多再试 6 次**。都不行就标为失败、不再自动重试；你的系统恢复后，可以请管理员在后台的“推送记录”里手工重发。
- 推送记录保留 30 天。

### 写接收程序时要注意的

- **同一条通知可能收到不止一次**（你应答慢了、管理员手工重发）。按 `id` 去重，或者把处理写成重复执行也没关系的。
- **通知不保证按发生的先后到达**（前一条在重试时后一条先到了）。不要拿通知里的状态直接覆盖你系统里的状态，以再取一次详情的结果为准。
- **推送不是百分之百可靠的**：你的系统停了一天多，通知就会重试完、标为失败。建议保留一个低频的拉取（比如每小时按 `updated_after` 拉一次订单）兜底。
- 一个应用只有一个接收地址。要发到两个系统，请管理员建两个应用。

## 八、常见的对接方式

**ERP 或仓库系统发货**

1. 每隔几分钟调 `GET /orders?status=1&updated_after=上次的时间`，把新的待发货订单拉过去；或者订阅 `order.paid`，收到通知后调订单详情。
2. 仓库发出后调 `POST /orders/{订单号}/ship` 回传快递单号。
3. 拉订单时如果发现之前拉过的订单变成了 4（已取消）、5（售后中）、6（已关闭），在自己系统里拦截发货。**发货前建议再调一次订单详情确认状态。**

**库存同步**

外部系统定时调 `POST /stock`。先用 `GET /skus` 核对两边的货号对得上。

**财务对账**

每天调 `GET /pay-trades?status=1&updated_after=…` 拿收款和退款流水，按 `channel_trade_no` 和支付渠道的账单核对；用 `GET /refunds?status=4` 拿退款明细。

## 九、安全建议

- 密钥相当于密码：只放在对接系统的服务器上，不要写进前端页面、App 或发到聊天群里。
- 一个外部系统用一把密钥，只给它用得到的权限。
- 对方的出口 IP 固定时，在后台给应用填上 IP 白名单。
- 怀疑密钥泄露时，在后台重新生成，旧的马上失效。
- 发货、改单号、改库存这些写操作，后台“开放接口 → 调用记录”里都有记录；订单日志和库存日志里也会写明是哪个应用做的。
- 用了主动推送的话：接收地址用 https，收到通知一定要验证签名；签名密钥和接口密钥一样只放在服务器上，怀疑泄露时请管理员重新生成。

## 十、现在没有的

- 主动推送里没有的事件：修改物流单号、售后被拒绝或撤销、库存变动、支付流水。
- 通过接口创建或修改商品、改价格、创建订单、审核或发起退款。
- 分销佣金、提现、发票的数据。
- 取消发货、电子面单取号。
